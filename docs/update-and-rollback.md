# 自动更新与回滚说明

## 1. 信任链

```
发布私钥（发布机，离线）
   └─ 签名 manifest.json（ECDSA P-256 / SHA-256，覆盖除 signature 外全部字段，按字段名排序规范序列化）
        └─ manifest.sha256 指定更新包哈希
             └─ 更新器二次校验包 SHA-256，再解压安装
客户端内置公钥（编译期嵌入 FNSyncPlus.Core）
```

任一步失败都会停止：签名错、包哈希不符、解压越界、缺少主程序、启动验证失败。

## 2. 清单字段与策略

| 字段 | 作用 |
|---|---|
| `channel` | `stable` / `beta`。Stable 客户端永不接收 beta 清单；Beta 可接收两者 |
| `version` / `min_version` | 必须严格大于当前版本，否则按降级拒绝 |
| `min_compatible_client` | 客户端过旧时要求手工安装，不做跨代自动升级 |
| `batch` / `audience` | 分批灰度：客户端 `ReleaseBatch` 小于清单 `batch` 时不升级；`audience` 不匹配也不升级 |
| `url` | 必须 HTTPS |
| `size` / `sha256` | 下载后逐字节校验，不符即删除 |

## 3. 安装时序（关键安全点）

1. 用户在「设置 → 软件更新」点击「安装并重启」。
2. `UpdateService.PrepareInstallAsync`：
   - 进入维护状态（`TaskManager.EnterMaintenanceHold`），**不再启动新的备份任务**；
   - 等待正在运行的备份自然结束，最多等待预算时间；
   - 复查是否存在结果不明确的提交或未释放的锁；有则**拒绝**安装；
   - 保存配置。
3. 启动 `FNSyncPlus.Updater.exe --apply ... --wait-pid <当前进程>`。
4. 主程序退出；更新器等待该 PID 真正退出（超时则放弃安装，不会强杀）。
5. 更新器解压到 `.update-work\extract-*`，安装到 `app-<新版本>\`，写 `current.json`，旧指针存入 `previous.json`，全部记入 `update.log`。
6. 启动验证：拉起新版本，等待它写 `.health\<版本>.healthy.json`（主窗口可用后写入）。超时或进程退出即判定失败。
7. 失败 → 指针回滚到 `previous.json` 并重新启动旧版本；**失败的版本目录保留**用于排查。
8. 成功 → 清理解压目录。

## 4. 回滚

自动回滚：启动验证失败时更新器自动切回上一版本。

手工回滚：

```powershell
& "$env:LOCALAPPDATA\Programs\FNSyncPlus\FN_Sync_Plus.exe" `
  --layout "$env:LOCALAPPDATA\Programs\FNSyncPlus" --rollback
```

**数据格式保护**：`DataFormatGuard` 在同机记录配置格式版本。若新版把格式升级到 3，而旧版只支持 2，旧版会拒绝启动并提示安装最新版本，而不是写坏配置。因此：

- 程序二进制可以回滚；
- 数据格式不能靠回滚“降级”；
- 需要真正降级时，必须先备份 `%LOCALAPPDATA%\FNSyncPlus`，由开发者提供迁移工具。

## 5. 更新日志与操作状态

`<安装根目录>\update.log`，追加式，包含：applying / installed / launch 结果 / 回滚 / 拒绝原因。日志不含凭据与 NAS 路径。

每次安装拥有唯一操作 ID（`--operation-id`，GUID）。更新器日志中属于本次安装的行带 `[op <id>]` 前缀标记，看门狗只依据**本次操作**的标记行判断结果，绝不搜索历史日志中的 installed / failed / rolled back 等模糊字样。

除日志外，每次操作还有独立状态文件 `<安装根目录>\.ops\<操作ID>.json`，原子写入，记录：操作 ID、目标版本、时间戳、更新器进程身份（PID + 启动时间 + 可执行路径 + 操作 ID 四元组）、状态（WaitingForAppExit / Installing / Installed / RolledBack / Abandoned / FailedBeforeInstall / Unknown）与失败原因。主程序重启后按状态文件对账：进行中但更新器已消失的操作标记为 Unknown 并阻止该版本自动重装，等待人工诊断。

## 6. 签名密钥轮换与吊销策略

### 6.1 算法现状（以代码为准）

签名链全环节一致使用 **ECDSA P-256（nistP256）/ SHA-256**：`UpdateManifestSigner`（签名）、`UpdateManifestVerifier`（验签）、`PinnedUpdateKey`（客户端嵌入公钥）、离线工具 `FNSyncPlus.UpdateTool` 与 `build-release.ps1`。第三轮报告中的 "ed25519" 系误述，已修正；实现保持现有经测试的 ECDSA P-256 不变。签名覆盖清单除 `signature` 外的全部字段，按键名排序做规范 JSON 序列化后签名。

### 6.2 密钥保管

- 发布私钥（PKCS#8 PEM）仅存于离线发布机，**绝不进入代码仓库、CI 制品、更新服务器或任何客户端设备**。
- 公钥（SPKI PEM）在编译期经 `-p:UpdatePublicKeyPath` 嵌入 `FNSyncPlus.Core` 程序集资源（`FNSyncPlus.update-public.pem`）。客户端只信任这一枚嵌入公钥；无公钥时更新能力整体停用（fail-closed），不静默降级为不验签。

### 6.3 轮换流程（计划内更换密钥对）

1. 在离线发布机生成新密钥对（`UpdateTool keygen`）。
2. 用**当前（旧）私钥**签发一个常规更新包，该版本的客户端编译时嵌入**新公钥**（`-p:UpdatePublicKeyPath=<新公钥>`）。清单照常由旧私钥签名——旧客户端用旧公钥验证通过，升级完成后客户端内嵌的已是新公钥。
3. 确认目标设备群已升级到新公钥版本后（按版本遥测/台账核对），发布机切换用**新私钥**签发后续清单，旧私钥离线封存。
4. 轮换窗口内若仍有旧公钥版本的客户端，它无法验证新私钥签名的清单（按"签名无效"拒绝并停留在安全状态），需先用旧私钥签发的包完成过渡。可利用 `min_compatible_client` 字段强制旧客户端先升到过渡版本。

### 6.4 吊销（私钥泄露或怀疑泄露）

1. **立即停止使用泄露私钥签发任何新清单**，并通知试点 IT 暂停更新通道（取下更新服务器清单或返回 404——客户端对无法获取/验证清单本就按安全失败处理）。
2. 评估暴露面：持有泄露私钥的攻击者可伪造"合法签名"的恶意清单，但还需同时控制 HTTPS 更新源并满足版本递增/通道/批次策略才能投递；SHA-256 与 HTTPS 不能替代吊销，只是纵深。
3. 在离线发布机生成新密钥对，用**泄露的私钥最后一次**签发一个强制升级包（嵌入新公钥，版本号高于一切已发布版本，必要时收紧 `audience` 只面向受影响批次），推送给全部受影响设备。
4. 确认全量迁移后，在发布台账中**显式吊销并销毁泄露私钥**，登记吊销时间、影响版本范围、过渡包版本号。
5. 每次轮换/吊销事件写入发布台账（密钥指纹、启用日期、停用日期、签发人、原因），作为企业验收材料的一部分。

### 6.5 当前状态

- 测试/试点使用一次性隔离密钥对，**不作为正式生产信任根**。
- 正式生产密钥对的生成仪式、保管责任人、轮换周期（建议 12 个月或人员变更时）与吊销演练，属于企业部署验收的未完成事项（BLOCKED，见验收报告）。

## 7. 已知限制（必须在试点前知晓）

- **没有正式代码签名证书**：安装包与主程序未做 Authenticode 签名，SmartScreen 会提示。内部试点需按公司策略放行，不得对外分发。
- **没有真实内网更新服务器**：当前仅用本地回环 HTTPS 服务与一次性测试密钥验证，尚未在公司服务器上部署与验收（BLOCKED）。
- **无人值守安装默认关闭**：需在设置中显式选择「无人值守安装」并打开开关；且在正式签名与验收完成前不得在公司生产电脑启用。
- **安装器未在本环境编译**：`FNSyncPlus.iss` 已写好，但当前机器没有 Inno Setup，未产出 `setup.exe`（BLOCKED）。
